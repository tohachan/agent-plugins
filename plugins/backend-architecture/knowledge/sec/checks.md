# Security — audit checklist

> **Scope:** protecting the API, its data and its runtime: the OWASP API Security Top 10 (2023) as concrete checks, authentication and token handling, authorization models and tenant isolation, input handling and injection, password storage, secrets, transport security, browser-facing controls (CORS, CSRF, headers), security logging and audit trails, supply chain, container and cloud least privilege, data protection. **Hands off to:** rate-limit algorithms, timeouts, load shedding → RES · per-tenant quotas and isolation by cells → SCALE · response shape, versioning, error format, pagination contract → API · log pipeline, alerting, retention tooling → OBS · CI/CD pipeline, config delivery, image build/deploy mechanics → OPS · webhook replay/dedup semantics → IDEM · DB roles and schema details → DATA.

## Audit checklist

| ID | Check | Evidence / search hints | Default severity |
| --- | --- | --- | --- |
| `SEC-CHK-1` | (API1) Is every object access scoped to the caller/tenant in the query? | Handlers taking `:id`/`{id}` params; Go `r.PathValue("id")`, `chi.URLParam`; Node `req.params.id`. Fail if the lookup (`FindByID`, `findUnique({ where: { id } })`, `SELECT ... WHERE id = $1`) has no owner/tenant predicate or follow-up check. Check bulk, export, file-download and GraphQL `node` paths; test with a second account. SEC-BP-1, BP-3, AP-6 | Critical |
| `SEC-CHK-2` | (API2) Are tokens verified with pinned algorithms and full claim validation? | Go: `ParseUnverified`, `jwt.Parse` without `WithValidMethods`/`WithAudience`/`WithIssuer`, keyFunc ignoring `token.Method`. Node: `jwt.decode(`, `verify(` without `algorithms`, `audience`, `issuer`; custom base64 splitting. Fail on any unverified path that feeds authz. SEC-BP-5, BAD-1, BAD-2 | Critical |
| `SEC-CHK-3` | (API2) Are sessions/tokens short-lived, rotated and revocable, and is login hardened? | Token TTL config (`expiresIn`, `exp` set), refresh rotation and reuse detection, session timeouts, rate limit on `/login`, `/reset`, `/otp`; MFA for admins; account-enumerating messages. Fail: access tokens > 1 h with no revocation, no brute-force limits. SEC-BP-6, BP-7, AP-5 | High |
| `SEC-CHK-4` | (API3) Are inputs bound to explicit DTOs and outputs filtered? | Go: `Decode(&` into types that have `Role`, `IsAdmin`, `TenantID`, `OwnerID`, `Balance` fields; missing `DisallowUnknownFields` on such paths. Node: `req.body` passed to `create`/`update`/`save`, `Object.assign(`, spread of `req.body`. Responses: `res.json(entity)`, `json.Marshal` of DB models; look for `password`, `hash`, `token` fields in API output. SEC-BP-8, BAD-4, BAD-5 | High |
| `SEC-CHK-5` | (API4) Are body size, upload, page size, timeouts, query complexity and rate limits bounded? | Go: `http.Server` without `ReadHeaderTimeout` (gosec G112), `io.ReadAll(r.Body)` without `MaxBytesReader`. Node: `express.json({ limit` raised to MBs, `multer` without `limits`, GraphQL without depth/complexity plugin. Gateway rate limits. Fail: any unbounded user-controlled size or cost. SEC-BP-10 | High |
| `SEC-CHK-6` | (API5) Is function-level authorization enforced by default on every route, including admin? | Router setup: routes registered outside the auth middleware group, `/admin`, `/internal`, `/debug` paths, HTTP method variants (`PUT` protected but `PATCH` not). Fail: any state-changing route reachable by a lower role; confirm with the role × route matrix. SEC-BP-2, AP-2 | Critical |
| `SEC-CHK-7` | (API6) Are abuse-prone business flows protected beyond generic rate limits? | Signup, checkout, coupon/referral, SMS/email/OTP sending, password reset, free trials: per-account/per-device limits, CAPTCHA/bot detection, spend caps on SMS/LLM providers. Fail: a script can drain money or inventory. SEC-BP-10 | High |
| `SEC-CHK-8` | (API7) Are server-side fetches of user-influenced URLs restricted? | Go: `http.Get(` / `client.Do` with URLs from requests, webhooks, image/import/preview/OIDC discovery features; no dialer `Control` IP check. Node: `fetch(`/`axios(` with `req.body.url`. Check IMDSv2 enforcement, egress policy. Fail if internal IPs/metadata are reachable. SEC-BP-11 | High |
| `SEC-CHK-9` | (API8) Is production configuration secure (CORS, headers, cookies, CSRF, errors, debug)? | `cors({ origin: '*'`/`origin: true` with `credentials`, Go `AllowedOrigins: []string{"*"}` + `AllowCredentials`; `helmet` absent; cookie flags; CSRF protection for cookie-auth mutations; stack traces in error handlers (`err.stack` in responses, `fmt.Fprintf(w, err.Error())` for DB errors). SEC-BP-15, BAD-12, BAD-13 | High |
| `SEC-CHK-10` | (API9) Is there a current inventory, with old versions and debug surfaces removed from public exposure? | OpenAPI/proto specs vs registered routes, `/v1` still live, Swagger UI/GraphQL playground in prod, `net/http/pprof` on the public mux, `/metrics`/`/actuator`/`/debug` exposed, staging hosts with production data. SEC-BP-20 | Medium |
| `SEC-CHK-11` | (API10) Are upstream responses and inbound webhooks treated as untrusted? | Webhook handlers without signature verification or using parsed (not raw) body for HMAC, non-constant-time compare, no timestamp check; upstream JSON used without validation; clients following redirects with credentials. SEC-BP-12, BAD-14 | High |
| `SEC-CHK-12` | Is all SQL, NoSQL, shell and template use free of injection? | Go: `fmt.Sprintf`/`+` building SQL, `Raw(`/`Exec(` with formatted strings, `exec.Command("sh", "-c"`, `text/template` for HTML, `template.HTML(`. Node: template literals in `query(`, `$queryRawUnsafe`, `.raw(` with `${`, `child_process.exec`, `shell: true`, `eval(`, `new Function(`, Mongo `find(req.body` / `$where`, path joins with user input. Confirm the value is user-reachable. SEC-BP-9, BAD-6, BAD-7, BAD-8 | Critical |
| `SEC-CHK-13` | Are passwords hashed with argon2id/bcrypt/scrypt at adequate cost? | Go: `golang.org/x/crypto/argon2`, `bcrypt.GenerateFromPassword` cost; `sha256.Sum256(password`, `md5.`. Node: `argon2`, `bcrypt`, `crypto.createHash('sha256').update(password`. Fail on fast hashes or bcrypt cost < 10. SEC-BP-7, BAD-9 | Critical |
| `SEC-CHK-14` | Are secrets absent from git history, images and manifests, and managed with rotation? | `git ls-files | grep -E '\.env$|\.pem$|id_rsa'`, gitleaks/trufflehog over full history, Dockerfile `ENV`/`ARG` with `KEY|SECRET|TOKEN|PASSWORD`, k8s `Secret` YAML with `data:` in repo, CI variables printed. Fail on any live secret found (treat as compromised). SEC-BP-13, BAD-10 | Critical |
| `SEC-CHK-15` | Is TLS verified on every outbound connection and used on internal hops? | `InsecureSkipVerify`, `rejectUnauthorized: false`, `NODE_TLS_REJECT_UNAUTHORIZED`, `sslmode=disable|require`, Redis/Kafka clients without TLS, `MinVersion` below TLS 1.2, mesh mTLS mode `PERMISSIVE` in prod. SEC-BP-14, BAD-11 | High |
| `SEC-CHK-16` | Are logs free of secrets/PII, and do security events reach an append-only audit log? | Logger config (`redact`, `ReplaceAttr`), middleware logging headers/bodies (`morgan` custom tokens, `httputil.DumpRequest`), log samples; audit table permissions (app role has `UPDATE`/`DELETE`?), coverage of login, role changes, admin actions. SEC-BP-16, BAD-13, AP-7 | Medium |
| `SEC-CHK-17` | Is the supply chain controlled (lockfiles, scanning, update policy, SBOM, signing)? | `go.sum`/lockfile committed; CI runs `govulncheck ./...`, `npm audit --omit=dev` or OSV-Scanner and Trivy on images, failing on fixable High/Critical; `npm install` (not `ci`) in CI; lifecycle scripts allowed; actions pinned by SHA; SBOM generated. SEC-BP-17 | Medium |
| `SEC-CHK-18` | Do containers run non-root, read-only, with dropped capabilities and minimal base images? | Dockerfile: `USER`, base image (`FROM node:22` full vs `-slim`/distroless), build tools in final stage. k8s: `securityContext` fields, `privileged`, `hostPath`, `hostNetwork`, Docker socket mounts, PSA labels, NetworkPolicies. SEC-BP-18, BAD-16 | Medium |
| `SEC-CHK-19` | Are cloud IAM, DB and service accounts least-privilege and per service? | Terraform/IAM JSON with `"Action": "*"`/`"Resource": "*"`, shared roles across services, static access keys in CI instead of OIDC federation, app DB user owning schema or `SUPERUSER`, k8s RBAC `cluster-admin` bindings for workloads. SEC-BP-18, AP-4 | High |
| `SEC-CHK-20` | Is sensitive data minimised, encrypted at rest, and deleted on schedule? | Data classification doc; storage encryption flags (RDS `storage_encrypted`, bucket SSE-KMS), field-level encryption for restricted fields, retention jobs/TTLs, backups and logs covered, prod data in non-prod. Record the code part (classification, retention jobs covering every ingestion path, purge predicates that real data reaches — DATA-CHK-21) separately from the infrastructure part (encryption at rest, backup media): missing infrastructure evidence never makes the code part unverified, and a job's existence is not verification of the obligation. Fail: restricted data in plaintext columns or kept indefinitely without purpose. SEC-BP-19 | High |
| `SEC-CHK-21` | Can an elevated role apply an action to the actor's own record, or to records in which the actor has a conflicting interest? | Enumerate the authorization registry, policy table or route table — do not sample. For each write action admitting an elevated role (admin, operator, approver, support), check the decision when the target is the actor and when the target is tied to the actor (records they own or co-own, approval of their own request, their own limit, grant or payout). Look for guards such as `target == subject`, `own_row`, `notOwn…` in some modules and confirm the same decision in every other module and in bulk/import/batch, CLI and job paths. Fail: any path where an elevated role changes the inputs to its own outcome without an explicit, documented exception. SEC-BP-21, SEC-BP-22, SEC-AP-8 | High (Critical if it moves money or grants privileges) |
| `SEC-CHK-22` | Is every authorization or domain invariant enforced at every entry point that reaches the guarded state? | For each invariant found enforced somewhere (guard, policy clause, trigger, constraint), list all writers of the same state: other handlers, bulk and import paths, sheet/batch editors, operator CLI, background jobs, admin tools, database policies. A code index (call graph or symbol index such as graphify, LSP references, Sourcegraph) makes this enumeration reliable; without one, state the search method and its limits in the coverage section. Fail: one writer lacks the guard. SEC-BP-21, SEC-AP-8 | High |
| `SEC-CHK-23` | Do irreversible or high-impact decisions follow the separation-of-duties rule the domain requires? | Approval, publish, payout and grant flows: who may prepare, modify, confirm on behalf of others and approve; whether one principal can complete the whole chain; whether the decision is reversible. Compare with the project's specs; if they are silent, raise an owner question rather than a finding. Fail: documented separation not enforced. SEC-BP-22 | Medium (High where the domain mandates it) |

## Also scan for (rules not cited above)

Bodies: `knowledge/sec/rules.md`, looked up by ID.

- SEC-BAD-1 — Decoding a JWT without verifying it
- SEC-BAD-2 — Algorithm taken from the token header
- SEC-BAD-3 — Identity or role taken from the request
- SEC-BAD-4 — Request body decoded into domain/ORM models or passed straight to updates
- SEC-BAD-5 — Returning ORM entities or full rows
- SEC-BAD-6 — SQL built from strings
- SEC-BAD-7 — Shell commands with user input
- SEC-BAD-8 — Unsafe template and dynamic code use
- SEC-BAD-9 — Passwords hashed with MD5/SHA-1/SHA-256 (even salted) or encrypted reversibly; bcrypt fed >72 bytes silently
- SEC-BAD-10 — Secrets committed or baked in
- SEC-BAD-11 — TLS verification disabled
- SEC-BAD-12 — Permissive CORS
- SEC-BAD-13 — Secrets and PII in logs and error responses
- SEC-BAD-14 — Non-constant-time comparison of secrets
- SEC-BAD-15 — Weak randomness for security values
- SEC-BAD-16 — Container running as root with a writable filesystem and full capabilities
- SEC-AP-1 — Perimeter-only trust
- SEC-AP-2 — Authorization scattered as ad-hoc `if`s
- SEC-AP-3 — Homegrown authentication and crypto
- SEC-AP-4 — Shared god credentials
- SEC-AP-5 — JWT as an irrevocable session
- SEC-AP-6 — Tenant isolation by convention
- SEC-AP-7 — Logs and analytics as an ungoverned PII lake
