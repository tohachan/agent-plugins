# Observability — key decisions

> **Scope:** the signals that tell you what production is doing and why: structured logs, metrics, distributed traces, profiles, error tracking; SLIs/SLOs and error budgets; alerting, dashboards, runbooks, postmortems; audit vs debug logging. **Hands off to:** health/readiness semantics and degradation → RES; probe and rollout wiring → OPS; PII classification, secret handling and audit-log tamper-proofing → SEC; queue mechanics behind lag signals → MSG; latency budgets and profiling-driven optimisation → PERF; autoscaling on these signals → SCALE.

## Key decisions

| Decision | Options | Choose … when | Trade-off |
| --- | --- | --- | --- |
| Instrumentation API | vendor SDK (Datadog, New Relic agent) / OpenTelemetry SDK + OTel Collector | OTel by default in 2026: vendor-neutral, one context for logs/metrics/traces; vendor agent only when a single-vendor shop wants zero-config auto-instrumentation | OTel needs a Collector to run and tune; vendor SDK means re-instrumenting to switch backends |
| Trace sampling | head (parent-based ratio) / tail (Collector `tail_sampling`) / hybrid | head 1–10% when volume is high and only aggregates matter; tail when you must keep every error and slow trace; hybrid (head 10–25% then tail) at very high RPS | head is cheap but drops the interesting traces at random; tail needs all spans of a trace routed to the same Collector (load-balancing exporter by trace ID) and buffers memory for the decision wait (10–30 s) |
| Metrics transport | Prometheus pull (`/metrics`) / OTLP push / StatsD | pull for long-lived k8s workloads with service discovery; OTLP push for serverless, short jobs and when the backend is OTLP-native; StatsD only for legacy | pull needs scrape reachability and misses jobs shorter than the scrape interval; push needs backpressure and dedup on the receiver |
| Latency representation | averages / summaries (client quantiles) / histograms (fixed buckets) / native/exponential histograms | histograms always; exponential/native histograms where the backend supports them (Prometheus native histograms, OTel exponential) for accurate quantiles without bucket tuning | summaries cannot be aggregated across instances; fixed buckets must bracket the SLO threshold |
| Alerting basis | cause thresholds (CPU > 80%) / symptom SLO burn rate | page only on burn rate of user-facing SLIs; cause metrics go to tickets and dashboards | burn-rate needs agreed SLOs and good/total counters first |
| SLO window | rolling 28/30 days / calendar month | rolling for engineering decisions (no month-start amnesty); calendar only when tied to a contractual SLA | rolling windows are harder to explain to business owners |
| Collector topology | direct export from SDK / agent (DaemonSet or sidecar) / agent + gateway tier | direct only for small setups; agent for host metadata, local batching and retry; add a gateway when you need tail sampling, central redaction, multi-backend fan-out or egress control | each tier is another stateful-ish component to size and monitor (queue sizes, memory_limiter); direct export couples apps to backend outages |
| Error tracking | logs only / dedicated tracker (Sentry, Rollbar, vendor APM errors) | dedicated tracker once >1 service or a frontend exists: grouping, release regression, stack traces with source maps | another PII sink to scrub; event quotas cost money |
| Profiling | on-demand pprof/`--cpu-prof` / continuous (Pyroscope, Parca, vendor, eBPF) | continuous when CPU/memory cost matters or incidents are hard to reproduce; overhead with 100 Hz sampling is typically ~1–2% CPU | storage cost; profiles may contain symbol names only, but endpoints must not be public |
| Log retention tiers | single store / hot (7–14 d searchable) + cold (object storage) / separate audit store | tiered as soon as log spend is noticeable; audit logs always separate with compliance retention | cold logs are slow to query; separate stores need their own access control |
