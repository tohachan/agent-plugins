# Resilience — audit checklist

> **Scope:** keeping a service up and correct when its dependencies, its own instances or a whole failure domain misbehave: timeouts and deadlines, retries, circuit breakers, bulkheads, load shedding, rate limiting, backpressure, degradation, health checks, draining, redundancy, dependency SLAs, failure testing, and recovery dynamics (thundering herds, hedging, metastable failures). **Hands off to:** making retried writes safe → IDEM; worker shutdown, cancellation plumbing and bounded fan-out → CONC; broker redelivery and DLQs → MSG; capacity planning and autoscaling → SCALE; cache stampede protection → CACHE; SLOs, alerts and dashboards → OBS; abuse-oriented rate limiting and auth → SEC; deploy strategy and rollbacks → OPS; error/status contracts → API.

## Audit checklist

| ID | Check | Evidence / search hints | Default severity |
| --- | --- | --- | --- |
| RES-CHK-1 | Does each outbound operation have an effective deadline? | Trace all callers, contexts/signals, wrappers, clients and relevant proxies. `http.Client{}` is a lead, not a finding when a request deadline is enforced. Confirm a reachable unbounded path before reporting. RES-BP-1, RES-BAD-1. | By concrete impact |
| RES-CHK-2 | Do DB and cache clients have timeouts? | Postgres `statement_timeout`/`lock_timeout` (DSN or role), pool acquire timeout (`pgxpool` ctx, `pg` `connectionTimeoutMillis`), Redis `ReadTimeout`/`commandTimeout`. Fail: none set. RES-BP-1. | High |
| RES-CHK-3 | Are deadlines propagated and inner timeouts shorter than outer? | Go: `context.Background()`/`TODO()` in handler paths; timeouts derived from `r.Context()`. Node: `AbortSignal` passed down. Compare gateway/ingress (`proxy-read-timeout`), service and client timeouts. Fail: inner ≥ outer or chain broken. RES-BP-2, RES-BAD-2, RES-AP-2. | Medium |
| RES-CHK-4 | Are retries limited to idempotent, transient failures with exponential backoff and full jitter? | Grep `retry`, `backoff`, `axios-retry`, `p-retry`, `retry-go`, `cenkalti/backoff`, `hashicorp/go-retryablehttp`, gRPC `retryPolicy` JSON; inspect retryable conditions and HTTP methods. Fail: POST retried without idempotency key, fixed delay, no jitter. RES-BP-3, RES-BP-4, RES-BAD-3, RES-BAD-4. | High |
| RES-CHK-5 | Is there exactly one retry layer and a retry budget? | Mesh config (Istio `VirtualService.retries`, Envoy `retry_policy`/`retry_budget`, Linkerd `retry` annotations), SDK default retries (AWS SDK, Stripe), app wrappers, client SDKs. Fail: ≥ 2 layers retrying the same call, no budget. RES-BP-5, RES-BP-6, RES-AP-1. | High |
| RES-CHK-6 | Are slow/flaky dependencies guarded by circuit breakers counting timeouts? | Grep `gobreaker`, `failsafe-go`, `hystrix`, `opossum`, `cockatiel`; mesh `outlierDetection`. Confirm per-dependency scope and fallback in open state. Fail: none for optional dependencies called on hot paths. RES-BP-7, RES-BAD-11. | Medium |
| RES-CHK-7 | Are dependencies isolated by separate pools and concurrency caps? | Go `Transport.MaxConnsPerHost` (default 0 = unlimited), `MaxIdleConnsPerHost`; shared `http.DefaultTransport`. Node `http.Agent({ maxSockets })`, undici `Agent({ connections })`. Separate DB pools for batch. Fail: one unbounded shared pool. RES-BP-8, RES-BAD-10. | Medium |
| RES-CHK-8 | Does each instance cap in-flight work and shed excess early? | Middleware limiting concurrent requests, `MaxConcurrentStreams` (gRPC), ingress `limit-connections`, queue-time checks; load-test evidence of 503s instead of latency collapse. Fail: no admission control on a service with variable load. RES-BP-9, RES-AP-7. | High |
| RES-CHK-9 | Are per-client rate limits enforced with a correct scope and 429 + Retry-After? | Gateway config (Kong/Envoy/NGINX `limit_req`), `golang.org/x/time/rate`, `express-rate-limit`/`rate-limiter-flexible` and their store (memory vs Redis). Fail: in-memory limiter claimed as global; no limit on public API. RES-BP-10, RES-BAD-12. | Medium |
| RES-CHK-10 | Are queues and buffers bounded with backpressure? | Go `make(chan T, N)` with huge N or unbounded slices as queues; Node arrays as queues, streams without `pipeline`, ignored `write()` return; broker prefetch settings. Fail: unbounded buffering on overload path. RES-BP-11, RES-BAD-9, RES-AP-5. | Medium |
| RES-CHK-11 | Does each optional dependency have a tested fallback, and does no fallback fail open on security/money? | Read error branches of calls to optional services; metrics/tests for fallback activation; feature flags/kill switches. Fail: fallback returning permissive or zero values for auth/price. RES-BP-12, RES-BAD-13, RES-AP-6. | Medium (High if fails open on auth/money) |
| RES-CHK-12 | Are liveness, readiness and startup probes correctly scoped? | k8s manifests/Helm values: `livenessProbe`, `readinessProbe`, `startupProbe` paths and thresholds; read the handlers behind them. Fail: liveness hits DB/downstream; same handler for both; slow boot without startup probe. RES-BP-13, RES-BAD-5, RES-BAD-6, RES-AP-3. | High |
| RES-CHK-13 | Does the service drain gracefully? | Go: `signal.NotifyContext`/`signal.Notify` + `srv.Shutdown(ctx)`; Node: `process.on('SIGTERM'` + `server.close()`/`closeIdleConnections()`, `terminus`/`http-terminator`. k8s: `preStop`, `terminationGracePeriodSeconds` vs longest request. Fail: no handler, or grace period < preStop + max request. RES-BP-14, RES-BAD-7. | Medium (High if deploys cause visible errors) |
| RES-CHK-14 | Are Node server timeouts aligned with the load balancer? | `server.keepAliveTimeout`, `headersTimeout`, `requestTimeout` vs LB idle timeout (ALB 60s, GCP 600s, NGINX `keepalive_timeout`). Go: `http.Server` `ReadHeaderTimeout`, `IdleTimeout` set. Fail: app keep-alive ≤ LB idle; Go server with no `ReadHeaderTimeout`. RES-BAD-8. | Medium |
| RES-CHK-15 | Does redundancy meet agreed outage/recovery and capacity targets? | Map correlated failure domains and failover/headroom tests. Evaluate zone count, replicas and PDBs against requirements; a single zone is not automatically a defect. Missing requirements/evidence → unverified. RES-BP-15. | By concrete impact |
| RES-CHK-16 | Are dependency SLAs, timeouts and fallbacks documented and consistent with the service SLO? | Docs/ADRs listing dependencies per critical path; compute composite availability. Fail: SLO above what serial hard dependencies allow, unknown SLAs for critical providers. RES-BP-16, RES-AP-4. | Medium |
| RES-CHK-17 | Do clients recover with jitter and do new instances warm up? | Reconnect logic in WebSocket/SSE/broker clients, LB slow-start settings, breaker half-open probe count, cache warm-up. Fail: fixed-interval reconnects, instant full traffic to cold instances. RES-BP-17, RES-BAD-15. | Medium |
| RES-CHK-18 | Is hedging limited to idempotent reads under a budget? | Grep `hedge`, duplicate parallel requests, gRPC `hedgingPolicy`. Fail: hedged writes or unbounded hedging. RES-BP-18. | Medium |
| RES-CHK-19 | Are failure modes tested and are overload levers ready? | Toxiproxy/Chaos Mesh/Litmus/FIS configs, game-day records, runbooks with levers (disable retries, shed class, kill switch). Fail: no evidence that timeouts/breakers/fallbacks were ever exercised. RES-BP-19, RES-BP-20, RES-AP-8. | Medium |
| RES-CHK-20 | Do pools recover from failover, and is there no hidden shared SPOF? | Pool settings: pgxpool `MaxConnLifetime`/`HealthCheckPeriod`, `database/sql` `SetConnMaxLifetime`, node-postgres `maxLifetimeSeconds`/`idleTimeoutMillis`, gRPC server `MaxConnectionAge`. Map which services share one Redis/DB/NAT and its HA mode. Fail: no lifetime limit on pools to failover-capable endpoints; single non-HA instance shared by critical paths. RES-BAD-16, RES-AP-9. | High |
