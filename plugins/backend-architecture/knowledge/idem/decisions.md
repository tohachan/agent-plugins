# Idempotency & consistency — key decisions

> **Scope:** making repeated requests and messages safe (idempotency keys, natural idempotency, idempotent consumers), keeping state consistent across a DB and a broker or across services (outbox, CDC, sagas, 2PC), the consistency guarantees a system promises to readers, ordering and causality, reconciliation, ledgers, and side effects at third parties. **Hands off to:** retry policy, timeouts and backoff → RES; broker delivery guarantees, partitioning and DLQs → MSG; isolation levels, constraints and transaction mechanics → DATA; races and locks → CONC; HTTP method semantics and error contracts → API; replica lag and partitioning → SCALE.

## Key decisions

| Decision | Options | Choose … when | Trade-off | Rules |
| --- | --- | --- | --- | --- |
| How a write becomes idempotent | natural (unique business key, upsert, conditional state transition) / client idempotency key / server-generated token issued before the write | Natural when the entity has a stable business identity (order per cart, payment per invoice); client key for create-style POSTs with side effects; server token for flows where clients cannot generate keys reliably | Natural is cheapest but needs a real business key; keys need storage, TTL and in-progress handling; tokens add a round-trip | IDEM-BP-1, IDEM-BP-6, IDEM-BP-7, IDEM-BAD-1, IDEM-BAD-5 |
| Where idempotency records live | same DB/transaction as the business write / Redis / separate store | Same DB whenever possible — record and effect commit atomically; Redis only for non-critical dedup or where effect is itself idempotent | Same-DB adds rows and vacuum load; Redis can lose keys on failover/eviction and is not atomic with the DB write | IDEM-BP-2, IDEM-BP-5, IDEM-BAD-2, IDEM-BAD-4, IDEM-BAD-15 |
| How DB state and events stay in sync | transactional outbox + relay / CDC from WAL (Debezium) / listen-to-yourself (consume own event to update DB) | Outbox for explicit domain events with a stable schema; CDC when many tables or legacy code must emit changes without code changes; listen-to-yourself when the event is the source of truth (event sourcing) | Outbox needs a relay and cleanup; CDC couples consumers to table schemas unless combined with an outbox table; listen-to-yourself makes the write path async | IDEM-BP-8, IDEM-BP-9, IDEM-BAD-7, IDEM-AP-1 |
| Cross-service business transaction | single service owns it (redraw boundaries) / orchestrated saga / choreographed saga / 2PC/XA | Redraw boundaries first; orchestration when the requirements call for one place to see, time out and compensate state, or the flow branches (not by step count alone; IDEM-BP-10); choreography for 2–3 loosely coupled reactions; 2PC only inside one vendor's system that supports it natively | Sagas give up isolation (need semantic locks/countermeasures); orchestration adds a coordinator; choreography hides the flow; 2PC blocks on coordinator failure | IDEM-BP-10, IDEM-BP-11, IDEM-BP-21, IDEM-AP-2, IDEM-AP-4, IDEM-AP-5, ARCH-AP-9 |
| Consistency promised to readers | strong (linearizable) / read-your-writes / monotonic reads / bounded staleness / eventual | Strong for balances, inventory decisions, auth changes; read-your-writes for any UI that shows what the user just changed; eventual for feeds, search, analytics | Stronger reads go to the primary or wait for replication, costing latency and scale | IDEM-BP-14, IDEM-BAD-13, IDEM-AP-8 |
| Ordering scope | none / per-entity (partition key = entity ID) / global | Per-entity covers almost every business need; global only for small, single-partition streams | Global ordering caps throughput at one consumer; per-entity needs a key on every message and versioned updates | IDEM-BP-15, IDEM-BP-19, IDEM-BAD-12 |
| How drift is detected | none / periodic reconciliation against source of truth / continuous checks (invariants, sums) | Reconciliation whenever money, inventory or a third-party system of record is involved | Reconciliation is extra code and queries but is the only control that catches unknown bugs | IDEM-BP-16, IDEM-BP-17 |
| Money representation | mutable balance column / double-entry ledger with immutable entries, balance derived or cached | Ledger whenever real money, credits or quotas are involved and audit matters | Ledger needs more rows and a balance projection; mutable balance cannot explain itself | IDEM-BP-17, IDEM-BAD-11, IDEM-AP-7 |
| Long-running workflow modelling | implicit status flags / explicit state machine with a liveness check | Explicit state machine whenever a workflow has several actors or approvals | More upfront modelling; implicit flags can strand an item no actor may move on | IDEM-BP-21 |
