# Architecture styles & boundaries — key decisions

> **Scope:** the macro shape of a system (monolith, modular monolith, microservices, serverless, event-driven), how it is cut (bounded contexts, business capabilities, data ownership), how parts talk (sync vs async, gateway/BFF), the internal structure of one service (layered, hexagonal, clean), coupling, Conway's law, migration (strangler fig) and decision records. **Hands off to:** endpoint and contract design → API; broker semantics, delivery guarantees, event schemas → MSG; sagas, outbox, cross-service consistency → IDEM; timeouts, retries, circuit breakers on inter-service calls → RES; partitioning and horizontal scaling → SCALE; per-service DB schema and migrations → DATA; service-to-service auth → SEC; pipelines and deploy independence mechanics → OPS.

## Key decisions

| Decision | Options | Choose … when | Trade-off |
| --- | --- | --- | --- |
| Deployment shape | monolith / modular monolith / microservices / serverless functions | modular monolith by default up to ~3–5 teams (≈ 30–50 engineers) or while the domain is still being discovered; microservices when teams are blocked on each other's releases, parts need very different scaling/availability/tech, and the org already runs CI/CD, tracing and on-call per team; serverless for spiky, event-triggered or low-traffic workloads with short (< 15 min) units of work | microservices buy team autonomy and independent scaling at the price of network failure modes, distributed data, and a platform tax (≈ 1 platform engineer per 5–10 service teams); serverless trades ops for cold starts, vendor limits and harder local testing |
| Where to cut | technical layers (UI/API/DB services) / entities (User, Order services) / business capabilities and bounded contexts | business capability/bounded context always; a candidate boundary is good when most changes land inside one side and the pair talk through a small, stable contract | finding contexts takes domain discovery (event storming, context mapping); wrong cuts are expensive to undo once data is split |
| Data ownership | shared database / schema-per-service on shared cluster / database per service | one owner per table always; a shared physical cluster with separate schemas and credentials is fine early; separate instances when isolation, scale or blast radius demand | separate DBs lose joins and ACID across contexts → replication via events, API composition, IDEM patterns |
| Interaction style | sync request/response (HTTP/gRPC) / async commands / async events (pub/sub) / event-carried state transfer | sync when the caller needs the answer to proceed and the call chain is ≤ 2–3 hops; async events when the producer doesn't care who reacts and eventual consistency is acceptable; event-carried state when consumers need the data locally to avoid runtime coupling | sync = temporal coupling and multiplicative availability (5 hops at 99.9% ≈ 99.5%); async = eventual consistency, harder debugging, need for idempotent consumers (→ IDEM, MSG) |
| Edge composition | clients call services directly / single API gateway / BFF per client type / GraphQL federation | gateway for cross-cutting edge concerns (TLS, authn, rate limits, routing); BFF when web/mobile/partners need materially different shapes and a frontend team owns it; federation when many teams contribute to one graph | gateway risks becoming a business-logic monolith; BFF duplicates aggregation; federation needs schema governance |
| Internal service structure | transaction script / layered (handler→service→repo) / hexagonal (ports & adapters) / clean (use-case centric) | transaction script for CRUD-dominant, thin-logic services; layered for moderate logic; hexagonal when rich domain rules need testing without infra or adapters genuinely vary (multiple inbound channels, swappable providers) | every extra layer is indirection and mapping code; too little structure lets SQL and HTTP leak into domain rules |
| Integration with another context | conformist / anti-corruption layer (ACL) / open-host service + published language / shared kernel | ACL when the upstream model is legacy, external or awkward; open-host when you serve many consumers; conformist when the upstream is good and you have no leverage; shared kernel only between two closely cooperating teams on a tiny, versioned model | ACL is code to maintain; conformist imports upstream churn; shared kernel couples release cycles |
| Event style | notification events (ID + type, consumer calls back) / event-carried state transfer (full snapshot) / event sourcing | notification for low-volume, loose-coupled cases; state transfer when consumers need local read models and you want to avoid callback storms; event sourcing only when audit history *is* the domain (ledgers) and the team has done it before | notifications create callback load and runtime coupling; state transfer exposes schema and needs versioning; event sourcing adds projections, upcasting and replay complexity |
| Migration path from a legacy system | big-bang rewrite / strangler fig / branch by abstraction inside the codebase | strangler fig (route-by-route behind a facade) for anything in production that earns money; branch by abstraction for replacing a component inside one deployable | strangler means running two systems and syncing data for months; big-bang rewrites fail more often than they finish |
| Decision record | none / wiki pages / ADRs in repo | ADRs (`docs/adr/NNNN-title.md`, status Proposed/Accepted/Superseded) for any decision expensive to reverse: style, boundaries, data store, sync vs async | a few minutes per ADR; requires discipline to supersede rather than edit |
