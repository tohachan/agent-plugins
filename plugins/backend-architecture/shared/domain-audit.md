# Domain review

Loaded only when the brief says `domain=on`, or by a backend design whose requirements name privileged roles, money movement, approvals or retention/deletion obligations. With `domain=off` this file is not read: its checks are not part of any area checklist, get no ledger rows and are not described as verified or excluded one by one. Apply checks only within the selected areas and mechanisms in a focused audit; a full audit covers every in-scope domain module.

The skill does not define the target's domain. Derive it from the target's own sources — specs, ADRs, contracts, policies, tests, code comments, the authorization registry — and record each invariant with its source, owner and every entry point that can violate it. For each domain module apply the checks below, with the same states, evidence rules and severities as area checks (`method.md`). Their IDs are stable; rule bodies resolve by Grep on the ID in `knowledge/<prefix>/rules.md`. The technical halves live in the area checklists (SEC-CHK-20, SEC-CHK-22), and area rules still apply inside a domain pass.

| ID | Check | Evidence / search hints | Default severity |
| --- | --- | --- | --- |
| SEC-CHK-21 | Can an elevated role apply an action to the actor's own record, or to records in which the actor has a conflicting interest? | Enumerate the authorization registry, policy table or route table — do not sample. For each write action admitting an elevated role (admin, operator, approver, support), check the decision when the target is the actor and when the target is tied to the actor (records they own or co-own, approval of their own request, their own limit, grant or payout). Look for guards such as `target == subject`, `own_row`, `notOwn…` in some modules and confirm the same decision in every other module and in bulk/import/batch, CLI and job paths. Fail: any path where an elevated role changes the inputs to its own outcome without an explicit, documented exception. SEC-BP-21, SEC-BP-22, SEC-AP-8 | High (Critical if it moves money or grants privileges) |
| SEC-CHK-24 | Is every domain invariant enforced at every entry point that reaches the guarded state? | For each invariant found enforced somewhere (guard, policy clause, trigger, constraint) and each domain module, source and owner it was derived from, list all writers of the same state: other handlers, bulk and import paths, sheet/batch editors, operator CLI, background jobs, admin tools, database policies. A code index (call graph or symbol index such as graphify, LSP references, Sourcegraph) makes this enumeration reliable; without one, state the search method and its limits in the coverage section. Fail: one writer lacks the guard. SEC-BP-21, SEC-AP-8 | High |
| SEC-CHK-23 | Do irreversible or high-impact decisions follow the separation-of-duties rule the domain requires? | Approval, publish, payout and grant flows: who may prepare, modify, confirm on behalf of others and approve; whether one principal can complete the whole chain; whether the decision is reversible. Compare with the project's specs; if they are silent, raise an owner question rather than a finding. Fail: documented separation not enforced. SEC-BP-22 | Medium (High where the domain mandates it) |
| IDEM-CHK-21 | Can every non-terminal workflow state be left, and does no combination of rules strand an item? | Workflow/status enums, transition guards, readiness or "waits on" computations, refusals that apply after another actor's step (submit, lock, freeze, approve), close/finish gates requiring every item to be ready. For each waiting state: who may act, whether that action is still allowed after the preceding steps, and who is told. Fail: a reachable state with no permitted actor or job, recoverable only by a manual reopen. IDEM-BP-21. | Medium (High if it blocks a mandatory deadline or closure) |
| DATA-CHK-21 | Do documented retention and deletion obligations match the implemented purge and ingestion behaviour? (DATA-BP-21, DATA-BP-20, SEC-BP-19) | Find the obligation sources (specs, ADRs, privacy policy, retention register, contracts) and each store holding the data; for each, the job or TTL that enforces it, its predicate, and whether any code path ever produces rows matching it; sync/import paths that load already-expired records; audit and journal stores. "Verified" requires citing both the obligation and the mechanism that covers it. Fail: an obligation with no enforcing code, a dead predicate, or an ingestion path that bypasses it | High (legal/regulatory) |

Record domain invariants with their status in the report's coverage section.

Domain authorization: SEC-BP-21, SEC-AP-8 — a central policy layer proves the chokepoint exists, not that each role/target decision is right; check the matrix.
